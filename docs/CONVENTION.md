# E!ffect Backend 컨벤션

## 1. API

### 1.1 경로·필드
- 엔드포인트는 `effect-frontend/API-spring.md` 목록을 따른다.
- 모든 경로는 `/api` 아래 (`server.servlet.context-path=/api`).
- JSON 필드는 **snake_case** (`spring.jackson.property-naming-strategy=SNAKE_CASE`).
  - 예외: 쿼리 파라미터 `defectType`, `overDays`는 프론트가 보내는 이름 그대로 받는다.
- 날짜·시간은 ISO 8601 문자열 (`2026-11-18`, `2026-11-18T14:30:00`).

### 1.2 응답 형식
모든 응답은 `ResponseDto`로 감싼다.

```json
{ "code": "SUCCESS", "message": "요청이 성공적으로 처리되었습니다.", "content": { } }
```

| 상황 | HTTP | 본문 |
|---|---|---|
| 단건 조회 | 200 | `content`에 객체 |
| 목록 조회 | 200 | `content`에 `{ "items": [...], "total", "page", "size" }` |
| 본문이 필요 없는 성공 (수정·삭제 등) | **200** | `content: null`, 문구는 `SuccessMessage` |
| 오류 | 4xx / 5xx | `{ "code": "RMA_NOT_FOUND", "message": "RMA를 찾을 수 없습니다.", "content": null }` |

- 204는 사용하지 않는다.
- 컨트롤러는 `ResponseEntity.ok(ResponseDto.ofSuccess(...))`로 반환한다. 응답을 자동으로 감싸는 `ResponseBodyAdvice`는 쓰지 않는다.
- 목록 응답의 최상위는 항상 객체다 (배열을 최상위로 보내지 않음).

### 1.3 HTTP 상태 코드
| 코드 | 용도 |
|---|---|
| 400 | 입력값 오류, 요청 형식 오류 |
| 401 | 인증 실패·토큰 만료·토큰 무효 (프론트는 받으면 재발급을 시도하고, 실패하면 로그아웃) |
| 403 | 로그인은 되었지만 권한 부족 |
| 404 | 리소스 없음 |
| 409 | 중복 (아이디 등) |
| 500 | 예상하지 못한 서버 오류 |
| 503 | **AI 서버 장애 전용.** 다른 이유로 사용하지 않는다 (프론트가 AI 장애 배너를 띄움) |

## 2. 예외 처리

### 2.1 오류 코드
- `ErrorCode` 인터페이스를 도메인별 enum이 구현한다.
  - `CommonErrorCode`, `AuthErrorCode`, `UserErrorCode`, `RmaErrorCode`, `ReportErrorCode`, `AiErrorCode` ...
- 코드는 **이름 형식** (`RMA_NOT_FOUND`, `DUPLICATE_USERNAME`).
- 한 번 배포된 코드 값은 바꾸지 않는다.
- HTTP 상태 코드는 의미에 맞게 지정한다 (없음 → 404, 중복 → 409, 토큰 오류 → 401).

```java
@Getter
@RequiredArgsConstructor
public enum RmaErrorCode implements ErrorCode {
    RMA_NOT_FOUND(HttpStatus.NOT_FOUND, "RMA_NOT_FOUND", "RMA를 찾을 수 없습니다.");

    private final HttpStatus httpStatus;
    private final String errorCode;
    private final String message;
}
```

### 2.2 예외 던지기
- 비즈니스 오류는 `throw new ApiException(XxxErrorCode.YYY)`로 던진다.
- 조회 후 없으면 예외: `repository.findByIdOrThrow(id, RmaErrorCode.RMA_NOT_FOUND)`.
- `IllegalArgumentException`, `RuntimeException`을 직접 던지지 않는다.

### 2.3 입력 검증
- 사용자에게 보여 줄 검증 문구는 **프론트가 담당**한다.
- 백엔드는 `@Valid`로 같은 규칙을 다시 검증하고, 실패하면 400 `INVALID_INPUT` 한 줄로 응답한다.
- 필드별 상세 오류는 응답에 넣지 않고 서버 로그에만 남긴다.
- 서버만 알 수 있는 오류(중복, 존재 여부, 권한)는 구체적인 문구로 응답한다.

### 2.4 보안
- 500 응답에 예외 메시지·스택 트레이스를 넣지 않는다 (`"잠시 후 다시 시도하세요"` 고정).
- 로그인 실패는 아이디 없음과 비밀번호 틀림을 구분하지 않는다.
- 토큰·비밀번호·개인정보는 로그에 남기지 않는다.

## 3. 패키지 구조

```text
com.u1_2.effect
 ├── global          # 공통 (dto, exception, config, annotation, repository)
 ├── config           # 외부 연동 (jwt, redis, ai)
 └── {domain}        # user, rma, report, dashboard ...
      ├── presentation   # Controller, Request/Response DTO
      ├── application    # Service
      └── domain         # Entity, Repository, enum
```

## 4. 코드

### 4.1 포맷
- UTF-8, LF, 들여쓰기 4칸, 파일 끝 개행.

### 4.2 이름
| 대상 | 규칙 | 예 |
|---|---|---|
| 요청 DTO | `{동작}{도메인}Request` | `CreateRmaRequest`, `LoginRequest` |
| 응답 DTO | `{도메인}{용도}Response` | `RmaDetailResponse`, `RmaListResponse` |
| 서비스 | `{도메인}Service` | `RmaService` |
| 컨트롤러 | `{도메인}Controller` | `RmaController` |

- DTO는 `record`로 만든다.

### 4.3 Entity
- `@Setter`를 쓰지 않는다. 값 변경은 의미 있는 메서드로 한다 (`changeStatus()`, `review()`).
- `@NoArgsConstructor(access = AccessLevel.PROTECTED)`.
- 생성은 `@Builder` 또는 정적 팩토리 메서드.
- enum은 `@Enumerated(EnumType.STRING)` (ORDINAL 금지).
- 생성·수정 시각은 `BaseTimeEntity`를 상속한다.

### 4.4 트랜잭션
- 서비스 클래스에 `@Transactional(readOnly = true)`, 쓰기 메서드에만 `@Transactional`.
- 컨트롤러에는 트랜잭션을 걸지 않는다.

### 4.5 시간
- `LocalDateTime` 사용, 서버·DB·JVM 시간대는 `Asia/Seoul`.

### 4.6 로그
- `@Slf4j`만 사용한다 (`System.out.println` 금지).
| 레벨 | 용도 |
|---|---|
| `error` | 5xx, 예상하지 못한 예외 (스택 트레이스 포함) |
| `warn` | 4xx 비즈니스 예외 |
| `info` | 주요 흐름 (로그인 성공, 보고서 생성 등) |
| `debug` | 개발용 상세 정보 (prod에서는 끔) |

### 4.7 주석·문서
- 주석은 한국어.
- 컨트롤러 메서드에는 Swagger `@Operation(summary = "...")`를 붙인다.

## 5. DB

| 항목 | 규칙 |
|---|---|
| 테이블·컬럼 이름 | snake_case, 테이블 이름은 단수 (`rma`, `report`, `users`*) |
| PK | `id BIGINT GENERATED BY DEFAULT AS IDENTITY` |
| 공통 컬럼 | `created_at`, `updated_at` |
| 스키마 변경 | Flyway (`src/main/resources/db/migration`) |
| 마이그레이션 파일 | `V{번호}__{설명}.sql` (예: `V1__init.sql`, `V2__add_report_table.sql`) |

- 이미 적용된 마이그레이션 파일은 수정하지 않는다. 변경은 새 파일로 추가한다.
- `ddl-auto`: 모든 프로필 `validate`. 스키마는 Flyway 마이그레이션으로만 변경한다.

\* `user`는 PostgreSQL 예약어라 `users`를 쓴다.

## 6. 설정·환경

- 프로필은 **`local`, `prod`** 두 개.
  - `local`: 개발자 PC, `docker-compose`로 PostgreSQL·Redis 실행.
  - `prod`: EKS. 모든 값은 환경변수로 주입한다.
- 환경변수 이름은 Spring 규칙을 따른다 (`SPRING_DATASOURCE_URL`, `SPRING_DATA_REDIS_HOST`, `JWT_SECRET`).
- 비밀값(DB 비밀번호, JWT 키 등)은 코드·설정 파일에 넣지 않는다. `application-local.yml`과 `.env`는 `.gitignore`에 포함한다.

## 7. Git

### 7.1 브랜치
- `develop`: 메인 개발 브랜치. 직접 push 금지, PR로만 머지.
- 작업 브랜치: `{타입}/{설명}` (예: `feat/rma-list`, `fix/token-reissue`).

### 7.2 커밋 메시지
`{타입}: {설명}` (설명은 한국어, 마침표 없음)

| 타입 | 용도 |
|---|---|
| `feat` | 기능 추가 |
| `fix` | 버그 수정 |
| `refactor` | 동작 변경 없는 구조 개선 |
| `docs` | 문서 |
| `test` | 테스트 |
| `chore` | 빌드·설정·의존성 |

예: `feat: RMA 목록 조회 API 추가`

### 7.3 PR
- 제목은 커밋 메시지 규칙과 같다.
- 본문은 PR 템플릿을 따른다: **관련 이슈** / **작업 내용** / **리뷰 포인트** / **테스트**.
- 리뷰어 1명 이상 승인 후 **squash merge**.

### 7.4 이슈
- 작업 시작 전에 이슈를 만들고, PR 본문에 `close #이슈번호`로 연결한다.
